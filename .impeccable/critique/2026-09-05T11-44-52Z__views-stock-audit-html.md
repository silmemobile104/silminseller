## Design Specificity Verdict

**การประเมินแบบ LLM (Assessment A):** หน้านี้ไม่ได้รู้สึกเหมือนตาราง CRUD ทั่วไป — มีร่องรอยการออกแบบเฉพาะงานจริง: เลข IMEI เป็น `font-mono` สีเหลืองเป็นจุดยึดสายตาของทุกแถว, ช่องสแกนเป็น `inputmode="numeric"` พร้อม Enter-to-submit (ใช้กับเครื่องสแกนบาร์โค้ดได้ทันทีโดยไม่ต้องแตะเมาส์), บังคับถ่ายรูปกล่องเป็นหลักฐานก่อนยืนยันทุกครั้ง, และตัวเลขความคืบหน้า (`1/226 เครื่อง`) เป็นข้อความใหญ่ที่สุดในหน้า — ถูกต้องแล้วที่ยึดเอา "เหลืออีกเท่าไหร่" เป็นคำตอบเดียวที่หน้านี้มีไว้ตอบ จุดที่ยังลื่นไถลกลับไปเป็น CRUD ทั่วไปคือตาราง "สินค้าที่ต้องตรวจนับวันนี้" เอง ซึ่งมีโครงสร้างเหมือนหน้ารายการสินค้าทั่วไป (ค้นหา+filter+list/card toggle) ทั้งที่จริงๆ มันคือ checklist ที่คนต้อง "เคลียร์ให้หมด" ไม่ใช่แค่ดูผ่านๆ

**การสแกนแบบ Deterministic (Assessment B):** เครื่องมือ CLI (`detect.mjs`) รันแบบ degraded (ไม่มี HTML parser module ต้องถอยไป regex matching) ได้ผลลัพธ์ 0 findings — **ถือเป็นการนับไม่ครบ ไม่ใช่ใบรับรองว่าสะอาด** ส่วนตัว detector บนเบราว์เซอร์จริง (inject `detect.js` เข้าไปในหน้าที่ล็อกอินจริง) เจอ 76 จุดทั้งเอกสาร แต่ agent ตรวจสอบพิกัดจริงของแต่ละจุดแล้วพบว่ามีแค่ **28 จุดที่อยู่ใน `#view-stock-audit` จริง** ที่เหลือ 48 จุดเป็นการชี้ผิดไปที่ modal/หน้าอื่นที่ซ่อนอยู่ใน DOM เดียวกัน (sidebar, modal อ่านบัตรประชาชนของหน้าสมาชิก, ปุ่มพิมพ์บาร์โค้ดของหน้าฐานข้อมูล ฯลฯ) — เป็นตัวอย่างที่ดีว่าทำไมต้องกรองพิกัดก่อนเชื่อ raw count ของ scanner ที่สแกนทั้ง document

จุดที่ 28 รายการนี้แบ่งเป็น: `undersized-ui-text` ×13, `nested-cards` ×7 (ธงความเชื่อมั่นต่ำของตัวเครื่องมือเอง), `cramped-padding` ×4, `dark-glow` ×1, `line-length` ×1, `all-caps-body` ×1

**Visual overlays:** แท็บที่ agent ใช้ inject overlay ถูกปิดไปแล้วหลังเก็บหลักฐานเสร็จ (ตามขั้นตอนทำความสะอาด) — **ไม่มี overlay ค้างให้ดูสดๆ ตอนนี้** ถ้าต้องการดูภาพ overlay จริงต้องรันใหม่

### จุดที่สองฝ่ายขัดกัน / เสริมกัน

- **Detector จับสิ่งที่ LLM มองข้าม:** Assessment A ชม "หนึ่งการ์ดต่อหนึ่งเรื่อง" ว่าเป็นจุดแข็ง แต่ไม่ได้สังเกตว่า **ในโหมดมุมมองการ์ด แต่ละแถวสินค้าเป็น `elev-card` ซ้อนอยู่ข้างในการ์ดพาเนลใหญ่ที่ก็เป็น `elev-card` เหมือนกัน** — นี่คือ "การ์ดซ้อนการ์ด" ที่กฎการออกแบบของโปรเจกต์เอง (craft-floor) ระบุชัดว่า "nested cards are always wrong" ตัวเลข nested-cards ×7 ของ detector คือหลักฐานที่ยืนยันเรื่องนี้ตรงๆ ผมจึงปรับคะแนนข้อ 8 (Aesthetic/Minimalist) ลงจาก 3 เหลือ 2 ให้สอดคล้องกับหลักฐาน
- **False positive ที่ควรระวัง:** Assessment B ตรวจ 3 element ตัวอย่างที่ถูกแท็ก `undersized-ui-text` (`#expected-result-count`, `#expected-list-pill`, `#audit-progress-pct`) พบว่า font-size จริงคือ 12px ซึ่ง**สูงกว่า**เกณฑ์ 11px ของ detector — ถ้า 13 จุดที่ถูกแท็กส่วนใหญ่เป็น `text-xs` (12px) แบบนี้ ก็น่าจะเป็น false positive ไม่ใช่ปัญหาจริง แต่ agent ยืนยันตัวตนที่แน่นอนของทุกจุดไม่ได้ (ตารางเรนเดอร์ใหม่ระหว่างตรวจ) จึงเป็นคำถามเปิด ไม่ใช่ข้อสรุป
- **False positive ที่ค่อนข้างมั่นใจ:** `dark-glow` 1 จุด ตกที่ `<p class="font-medium text-ink">IPad Gen11</p>` ซึ่งไม่มีคลาส shadow ใดๆ ในซอร์ส — น่าจะเป็นการจับผิดของเครื่องมือ ไม่ใช่ปัญหาจริง

## Overall Impression

ตัวตรงกลางของงาน (สแกน→เห็นตัวเลขวิ่ง→เห็นแถวเปลี่ยนสถานะ) ทำได้ดีจริง และงาน distill รอบก่อนได้ตัดของซ้ำซ้อนออกไปมากจริง แต่มี **ช่องโหว่ใหญ่ที่สุดของทั้งหน้าคือปุ่ม "ส่งผลตรวจนับ" ไม่ได้ถูกผูกไว้เลย** — คนสแกนครบ 226 ชิ้นแล้วไม่มีทางส่งผลได้จากหน้านี้ นี่ไม่ใช่เรื่องความสวยงาม แต่เป็น broken workflow ที่ต้องแก้ก่อนเรื่องอื่นทั้งหมด รองลงมาคือรอยต่อจบงานที่เงียบเกินไป (ไม่มีความรู้สึก "เสร็จแล้ว") และการ์ดซ้อนการ์ดในมุมมองการ์ดที่ขัดกับกฎการออกแบบของระบบเอง

## What's Working

1. **ปุ่ม "กรอก IMEI นี้ลงช่องสแกน" ในทุกแถวที่รอสแกน** — ให้คนคลิกจากรายการเพื่อโหลด IMEI เข้าช่องสแกนแล้วเลื่อนจอไปหาโดยอัตโนมัติ เป็นตัวช่วยงานจริง ไม่ใช่แค่มีไว้ให้ดูอินเทอร์แอคทีฟ
2. **วางแถวโครงร่าง (skeleton) ก่อน await ทุกครั้ง** พร้อมคอมเมนต์ในโค้ดที่อธิบายบั๊กเดิมที่เคยเจอ (ซ่อนกล่องทั้งก้อนจนกว่าจะมีข้อมูลจริง ทำให้ skeleton ไม่เคยถูกมองเห็น) — เป็นการแก้ที่ถูกจุดและทีมส่วนใหญ่มักพลาด
3. **ป้ายสถานะ "ขายแล้ว" ใช้ทั้งสีและข้อความ ไม่พึ่งสีอย่างเดียว** — ปลอดภัยสำหรับคนตาบอดสีโดยธรรมชาติของการออกแบบ ไม่ต้องแก้เพิ่ม

**Sam (พึ่งพา accessibility):** โครงสร้างดีจริง — focus ring ขึ้นสีเหลืองถูกต้อง, label มี `for=` ครบ, ปุ่มไอคอนมี `aria-label` — ยืนยันแล้วจากการทดสอบจริง จุดเสี่ยงเดียวคือ error ที่มีแค่ toast ชั่วคราว ผู้ใช้ screen reader มีหน้าต่างเวลาจับสัญญาณสั้นกว่าคนมองเห็นมาก

**Casey (ใช้มือถือระหว่างทำงาน):** ตารางในหน้านี้ใช้กลยุทธ์เลื่อนแนวนอน (`whitespace-nowrap` + `overflow-x-auto`) ไม่ยุบเป็นการ์ดอัตโนมัติบนจอเล็กตามที่ DESIGN.md §11.6 บันทึกไว้ — หมายความว่าบนมือถือจะเจอตาราง 6 คอลัมน์ที่ต้องเลื่อนซ้ายขวา ซึ่งไม่เข้ากับการใช้งาน "เหลือบดูระหว่างต้อนรับลูกค้า" ของเครื่องมือภายในแบบนี้ *(ไม่ได้ทดสอบสดเพราะปรับขนาดวินโดว์เบราว์เซอร์ไม่ได้ในสภาพแวดล้อมนี้ — สรุปจากการอ่านคลาส Tailwind และเอกสารโดยตรง)*

## Minor Observations

- ปุ่ม "ล้างทั้งหมด" ของชิปตัวกรองโผล่เมื่อมีตัวกรองมากกว่า 1 ตัวเท่านั้น ตรงตามกฎ DESIGN.md §11.5 แล้ว
- รูปกล่องในตาราง "รายการที่สแกนแล้ว" มี `hover:ring-1` บอกว่าคลิกขยายได้ — ไมโครอินเทอร์แอคชันเล็กๆ ที่ถูกต้อง
- ทั้งสองธีม (มืด/สว่าง) ยังคงใช้สีเหลือง accent เป็นสัญญาณ "กดได้" เพียงสีเดียวสม่ำเสมอ ไม่พบการเจือจาง

## Questions to Consider

1. ปุ่มส่งผลที่หายไปเป็นบั๊กจริง หรือเป็นการตัดสินใจแล้วว่าให้ฝั่ง "พนักงานสต็อก" เป็นคนกดปิดรอบจากหน้า review แทน? ควรถามเจ้าของโปรดักต์ก่อนแก้เป็น P0
2. ถ้าผ่อนกฎ "ถ่ายรูปทุกครั้ง" เป็น "ถ่ายรูปครั้งแรกของสินค้านั้นในวันนี้" ความแม่นยำจะเสียไปจริงไหม หรือแค่แก้ปัญหาความไว้ใจที่ถ่ายทุกครั้งก็แก้ได้เหมือนกัน?
3. ถ้าให้รายการ "สินค้าที่ต้องตรวจนับ" เริ่มต้นแบบย่อทันทีที่ session มีการสแกนอยู่แล้ว จะทำให้ "ขยายดูทั้งหมด" กลายเป็นการกระทำที่ตั้งใจ แทนที่จะเป็นสถานะเริ่มต้นที่รก?
